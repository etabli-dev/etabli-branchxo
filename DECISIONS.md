# DECISIONS — branchxo

Build-phase notes on design choices and deviations from the spec.

## In-spec choices

### Multiverse representation
Each `Universe` stores ONLY its own divergent moves (`moves`), `parentId`, and
`parentPly`. The full move list at any node is reconstructed by walking up the
parent chain and concatenating `parent.moves.slice(0, parentPly)` recursively
(see `fullMoves`). This keeps every universe immutable and makes "parent
untouched after fork" trivially true: the only data a fork adds is the new
child node.

We also cache `board` and `status` on each universe for O(1) reads. An
invariant test (`assertTreeInvariants`) recomputes them from scratch and
asserts they match — guaranteeing the cache cannot drift.

### Strength function
Implemented exactly per spec. For each of the (up to 4) win lines through the
candidate cell, we count my marks `k` and opponent marks `m` on the **other
two cells of the line** (we never count the candidate itself, since it is by
definition empty before placement).
- only mine: `10^k`
- only opp: `10^m * 0.9`
- mixed: `0`
- empty: `1` (centrality)

This yields the required ordering: immediate win (100) > immediate block (90)
> threat-build (10) > centrality (1-4 across the cell's lines). Verified by
unit test.

### AI
- **Easy** uses `Math.random` by default but accepts a deterministic `rng` for
  tests.
- **Medium** picks the max-strength empty cell.
- **Perfect** is full minimax with a `Map<string, MinimaxResult>` cache keyed
  by `boardString|toMove`. We did NOT add symmetry canonicalization — the
  cache is small enough already (<5×10³ unique reachable positions) and
  adding canonicalization would complicate move-back-translation. Noted in the
  spec as "optional".
- Tie-breaking prefers shorter forced wins and slower forced losses (so the
  AI never "stalls" a winning position).

### Probability modes
- `probPerfect` returns a 0/1 distribution (exact outcome under optimal play).
- `probRandom` runs `R=300` rollouts by default, where both sides play the
  "easy" policy (random + take-win + block-loss). The rollout signature
  accepts both `rng` (for tests) and `shouldCancel` (so the UI can debounce
  and abort).

### Branch UX
We chose a **modal "branch?" confirmation** when the user taps a divergent
cell while scrubbed back, rather than auto-forking. This makes the multiverse
moment explicit and undoable. Forward play (tip-of-timeline) is never
prompted.

### Accessibility
- Cells (`BoardView`) and tree nodes (`MultiverseTree`) carry
  `accessibilityLabel`s describing position / outcome / "X to move".
- Marks are distinguished by **shape + color** (X = cross + blue; O = ring +
  orange) — Okabe-Ito accessible pair, so total-color-blind users still
  perceive the difference.
- Outcome colors on tree nodes also use distinct hues + shape changes (active
  node has a halo ring).

### Persistence
We persist the entire tree (`MultiverseTree`) plus all settings under
`branchxo:v1`. On hydrate we run `assertTreeInvariants` defensively — if the
stored tree fails the invariant check (e.g. corrupted), we silently reset to a
single root rather than crash.

## Deviations / deferrals

1. **Skia tree pan/zoom** is implemented with nested ScrollViews rather than a
   gesture-driven matrix transform. This is sufficient for trees up to ~50+
   nodes and ships immediately. A true pinch-zoom with `react-native-gesture-handler`
   + Reanimated worklets is on the polish/refine list (audit phase will flag
   if needed).
2. **Skia "O" mark** is drawn with a stroked `Circle` rather than via a Path —
   semantically equivalent, code is simpler.
3. **Symmetry canonicalization** in the minimax cache is intentionally
   omitted (see above). The cache is fast enough.
4. **Reanimated** is installed and the Babel plugin is configured, but the
   build pass does not yet use reanimated worklets for tile animations. This
   is in scope for the refine/polish pass.
5. **App icons / splash** are placeholder PNGs generated by a Node script in
   `assets/`. Matching SVG sources are in `assets/*.svg`. Final art will be
   produced for the submission pass.
6. **Web preview** works for layout but the touch hit-tests on cells are sized
   for native; not tuned for desktop pointer.

## Appearance and app language (2026-11-24)

Settings now ends with an **Appearance** section, the suite-wide setting of the
native Établi apps (`etabli-doc/ios/App/AppearanceModel.swift`), drawn with the
game's own segmented controls:

- **App language:** System / Deutsch / English. "System" follows the device's
  preferred languages (iOS `AppleLanguages`, including a per-app language set in
  iOS Settings; `navigator.languages` on the web) and falls back to English.
  Every string lives in `src/i18n/strings.ts` (no i18n library: two typed
  catalogues, checked for equal keys by a unit test). The UI switches at once.
  The game shows no system dialogs, so it does not write `AppleLanguages`;
  `CFBundleLocalizations` (en, de) lets iOS offer the per-app language.
- **Mode:** System / Light / Dark (`Appearance.setColorScheme`, so native
  sheets follow too) and seven **accent colours** in the owner's order of
  2026-11-24 (Coder blue default, green, yellow, orange, red, purple, graphite).
- Stored under `appearance.mode`, `appearance.accent` and `app.language` with
  the native apps' raw values, separately from the saved game (`branchxo:v2`):
  a preserved unreadable save never resets them. Unknown values, including the
  removed `teal` and `brown`, fall back to the defaults.
- On iOS, launch arguments such as `-appearance.mode dark -appearance.accent
  yellow -app.language de` set the starting values, as in the native apps; the
  simulator tours use this.

### The game palette stays on the game surfaces

BranchXO's colours carry game meaning: the Okabe–Ito X (blue cross) / O (orange
ring) pair, the outcome colours shared by the board, timeline, tree nodes and
outcome chips, and the viridis heat scale. They were designed for the navy game
ground; on the light Hugo Coder background the orange O and the O-win yellow
would drop well below 3:1, and changing them per mode would break the match
between the chips and the tree. So the **game surfaces keep the fixed game
palette in both modes**: the board, the timeline mini-boards, the multiverse
tree, the heat map, the probability chart and the outcome chips are navy tiles,
including their own cyan in-game highlight (top-move halos, active tree path,
turning point).

The **mode and accent apply to the UI chrome** around them: background, text
and panels use the Hugo Coder neutrals (#FAFAFA / #212121 text and so on); the
accent marks selected segments (an accent border on a selection fill), the hint
toggles, the selected timeline ply ring, the *New game* outline and the
*Branch* button. Selection fills are the accent at 16 % over the surface,
except for yellow and orange, which use the neutral text colour (owner rule: no
yellow shade in any background). Text on an accent fill is white in light mode
and #212121 in dark mode. `__tests__/appearance.test.ts` checks the colour
table, 4.5:1 contrast of every accent against the background and with its
on-accent text, the chrome text on every selection fill, and that no tint lies
in the 30–70° hue range.

### One-line labels

Buttons, segments, chips and toggles keep one line down to a 375-pt iPhone SE
in both languages by design; the final simulator screenshot review is pending. Where a German label
was too long, the visible label is shorter and the full text is the
accessibility label: *Universen* (Multiversum), *Verlauf* (Zeitverlauf),
*Zu zweit* (Zu zweit an einem Gerät), *Gegen Computer* (Gegen den Computer),
*Perfektes Spiel* / *Zufallsspiel* (Gegen …). The iOS home-screen name is
*BranchXO* (it was the truncated project name `etabli-branchxo`).
